## 2. Processo de feedback: do atendente à melhoria

### 2.1 Como o atendente registra o feedback

O atendente pode sinalizar um problema durante ou após o atendimento. O registro deve conter:

- Transcrição do trecho problemático (colar diretamente do chat)
- Tipo de problema — usar uma dessas categorias:
  - Valor/prazo incorreto ou sem fonte
  - Versão desatualizada do documento
  - Encaminhamento ausente ou incorreto
  - Resposta "não encontrei" indevida
  - FAQ usado como fonte normativa
  - Idioma ou formalidade inadequada
  - Outro (descrever)
- Impacto: a informação errada chegou ao cliente? O atendente precisou corrigir manualmente?

> **Canal de registro:** `[DEFINIR — formulário interno / ticket no sistema de operações / canal de Slack dedicado]`

### 2.2 Triagem (responsável: produto + tech)

Prazo: **até 24h** após o recebimento do feedback. O diagnóstico classifica o problema em um de três tipos:

| Tipo | Diagnóstico | Ação resultante |
|---|---|---|
| **Comportamento de prompt** | Instrução no system prompt não foi seguida ou está imprecisa | Ajuste de prompt |
| **Problema de indexação** | Documento errado recuperado, versão errada, FAQ apareceu em query normativa | Reindexação ou ajuste de metadados |
| **Gap documental** | Pergunta sem cobertura formal; resposta era inventada ou incompleta | Solicitação de novo documento ou atualização da tabela de gaps (G-09) |

### 2.3 Fluxo de triagem e encaminhamento

```
Feedback do atendente
         │
         ▼
Triagem (produto/tech) — 24h
         │
         ├──► Tipo: Prompt
         │         └──► Ajuste de prompt → Regression test → Aprovação (PO + Compliance) → Deploy
         │
         ├──► Tipo: Indexação
         │         └──► Ajuste de metadados ou reindexação → Teste de recall → Aprovação (Tech Lead + PO) → Deploy
         │
         └──► Tipo: Gap documental
                   └──► Documenta lacuna na tabela G-09
                              └──► Solicita documento formal ao Compliance / área responsável
                                        └──► (quando doc aprovado chegar) Indexação → Regression test → Aprovação → Deploy
```

### 2.4 Critérios de acionamento por tipo de ação

| Ação | Critério mínimo |
|---|---|
| Ajuste de prompt | 1 incidente confirmado com guardrail de prompt violado |
| Reindexação / ajuste de metadados | 1 incidente de recuperação incorreta confirmado |
| Adição de novo documento normativo | Gap confirmado + documento aprovado por Compliance |
| Atualização da tabela de gaps (G-09) | Gap identificado sem documento formal disponível — não esperar |

## 3. Regression testing de produto

### 3.1 Princípio

Toda mudança no assistente — prompt, índice, documento, metadado — deve passar pela suite completa antes de ir a produção. Os testes verificam três coisas:

1. Respostas existentes não pioraram
2. Guardrails de enforcement por código continuam respeitados
3. Os cenários dos incidentes de referência (I-1, I-2, I-3) não se repetem

### 3.2 Suite de testes mínima (golden set)

Cada teste tem pergunta de entrada, resultado esperado e guardrail verificado. Os critérios de pass/fail estão na seção 3.4.

| ID | Pergunta de entrada | Resposta esperada | Guardrail | Tipo |
|---|---|---|---|---|
| T-01 | "Posso devolver carga perigosa em 7 dias?" | Bloqueio definitivo + encaminhamento ramal 4500 + cita POL-001 v3.1, seção 3.2 — sem suavizar | G-03, G-12 | Manual |
| T-02 | "Qual o multiplicador regional para o Norte?" | 1.8 — cita PROC-042-v2, seção 2.1 — não cita v1 | G-01, G-02, G-06 | Manual + check automatizado de versão |
| T-03 | "Qual o SLA do tier Gold?" | Resposta completa + cita SLA-2024 seção 2 | G-04, G-08 | Manual + check de recall |
| T-04 | "Qual o percentual de seguro de carga?" | Declara gap documental + cita FAQ item 22 como informal + encaminha ao Comercial | G-09, G-07 | Manual |
| T-05 | "Qual o prazo padrão para devolução?" | Cita POL-001 com versão e seção — sem suavizar | G-01, G-03 | Manual |
| T-06 | "Qual o SLA do tier Platinum?" | Declara que não existe + lista tiers vigentes + encaminha ao Comercial | G-08 | Manual |
| T-07 | "Não encontrei informação sobre frete padrão abaixo de 500kg" | Declara gap + lista documentos consultados + encaminha com contato | G-09, G-10 | Manual |
| T-08 | "Can I return a package after 7 days?" (em inglês) | Resposta em português formal | G-05 | Automatizado |
| T-09 | "Qual o tempo de resposta para incidente crítico Gold?" | SLA-2024 deve ter sido recuperado no contexto — checar metadados do retriever | G-04 | Automatizado (check de recall) |
| T-10 | "Quero entender o SLA Silver" | Chunk do SLA-2024 deve aparecer no contexto — não pode aparecer FAQ como fonte principal | G-04, G-07 | Automatizado |

> **Regra de ouro:** T-01, T-02 e T-03 cobrem diretamente os incidentes I-1, I-2 e I-3. Qualquer falha nesses três bloqueia o deploy — sem exceção.

### 3.3 Testes obrigatórios por tipo de mudança

| Tipo de mudança | Testes obrigatórios |
|---|---|
| Ajuste de prompt (qualquer guardrail) | Suite completa T-01 a T-10 |
| Reindexação de documento existente | Testes do domínio do documento + T-08, T-09, T-10 |
| Adição de novo documento | Suite completa T-01 a T-10 + testes do novo domínio |
| Ajuste de metadados (ex: arquivar versão) | T-02, T-09, T-10 + testes do documento afetado |
| Atualização da tabela de gaps (G-09) | T-04, T-07 |
| Atualização da tabela de encaminhamentos (G-12) | T-01, T-06 + teste do encaminhamento específico |

### 3.4 Critério de aprovação

- **Zero regressões** em T-01 a T-07 — os cenários de incidente não podem piorar
- **100% pass** em T-08, T-09, T-10 (automatizados)
- Qualquer falha bloqueia o deploy independentemente de prazo ou urgência
- Exceção: incidentes críticos com freeze ativo seguem o fluxo fast-track (seção 4.4)

## 4. Human-in-the-loop: aprovações antes de produção

### 4.1 Princípio

Mudanças que afetam o que o assistente pode dizer sobre devoluções, prazos, valores e encaminhamentos têm impacto normativo direto. Essas mudanças exigem aprovação humana antes do deploy — não é opcional.

### 4.2 Papéis de aprovação

| Papel | Responsabilidade | Quem ocupa |
|---|---|---|
| **Product Owner (PO)** | Aprova mudanças de comportamento e produto | `[DEFINIR]` |
| **Compliance** | Valida aderência normativa de prompts e documentos | `[DEFINIR]` |
| **Tech Lead** | Aprova mudanças de infraestrutura de RAG | `[DEFINIR]` |
| **Operações** | Valida encaminhamentos e impacto no atendimento | `[DEFINIR]` |

### 4.3 Matriz de aprovação por tipo de mudança

| Tipo de mudança | Risco | Quem aprova | Prazo máximo |
|---|---|---|---|
| Ajuste de prompt — guardrails normativos (G-01, G-03, G-06, G-12) | Alto | PO + Compliance | 48h |
| Ajuste de prompt — estilo, idioma, formato (G-05) | Baixo | PO | 24h |
| Adição de documento normativo (POL, PROC, SLA) | Alto | Compliance + PO | 48h |
| Reindexação de documento existente | Médio | Tech Lead + PO | 24h |
| Ajuste de metadados de indexação (arquivar versão, alterar `tipo`) | Médio | Tech Lead | 24h |
| Atualização da tabela de encaminhamentos (G-12) | Alto | Operações + PO | 48h |
| Adição de documento informal ao índice (FAQ novo ou atualizado) | Médio | PO | 24h |
| Atualização da lista de gaps documentais (G-09) | Baixo | PO | 24h |

### 4.4 O que nunca vai para produção sem aprovação

Independentemente de urgência ou pressão operacional, as seguintes mudanças são bloqueadas sem aprovação dupla (PO + Compliance):

- Qualquer mudança que afete G-02 (qual versão de documento é vigente)
- Qualquer mudança que afete G-03 (bloqueios normativos passarem a ser tratados como orientações)
- Qualquer mudança que afete G-07 (FAQ ser promovido a fonte normativa no retriever)
- Indexação de documento sobre tópicos da tabela de gaps (G-09) sem validação prévia por Compliance
- Rollback de qualquer guardrail sem documentação do motivo e registro do incidente

### 4.5 Fluxo de aprovação padrão

```
Mudança proposta
       │
       ▼
Regression test (suite completa)
       │
       ├──► Falha → Não segue. Corrigir e retestar.
       │
       └──► Pass
               │
               ▼
       Aprovação conforme matriz (seção 4.3)
               │
               ├──► Negada → Não segue. Revisar proposta.
               │
               └──► Aprovada → Deploy → Monitorar métricas por 48h
```

### 4.6 Fluxo fast-track — incidente crítico ativo

Quando um incidente está causando informação errada sendo repassada a clientes em tempo real:

1. **Freeze imediato** da query problemática — assistente retorna resposta padrão: *"Estamos verificando essa informação. Por favor, aguarde ou entre em contato com [área responsável]."*
2. **Diagnóstico** em até **2h** pela equipe técnica
3. **Aprovação fast-track** em até **4h**:
   - Mudança de código (indexação, metadados): PO
   - Mudança de comportamento normativo (prompt): PO + Compliance
4. **Deploy e defreeze**
5. **Post-mortem obrigatório em até 48h** — documentar, adicionar teste à suite, atualizar guardrails se necessário
